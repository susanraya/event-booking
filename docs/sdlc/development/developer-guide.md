<!-- sdlc:auto:start overview -->
Event booking is a two-application repository generated by the Quorq AI SDLC platform: an Angular 22 single-page app (built with Vite and the Analog plugin) for browsing events, selecting seats, booking, and organiser management, and a Spring Boot 4.1 (Java 21) backend exposing a REST API. The frontend's screens were approved against a design and currently run on seeded sample data; the backend has only a health check and stub handlers for the approved API routes (events, seats, locks, auth, check-in, organiser event/layout management) backed by JPA repositories, Flyway migrations, and JWT-based organiser auth, with PostgreSQL (or an H2 fallback) as the database.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js and npm (for the Angular/Vite frontend)
- Java 21 (backend requires java.version=21 per pom.xml)
- Docker and Docker Compose (for local PostgreSQL via docker-compose.yml)
- No separate Maven install needed — use the bundled ./mvnw wrapper
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository
2. cd frontend && npm install
3. (optional) docker compose up -d to start the local Postgres 16 database defined in docker-compose.yml
4. cd backend && sh mvnw spring-boot:run — with no DATABASE_URL set, the backend falls back to an in-memory H2 database
5. In a second terminal, cd frontend && npm run dev to start the Vite dev server
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend DTOs live in app.service as *Request/*Response classes; JSON field naming is snake_case per-DTO via @JsonNaming (not a global strategy), except the seating layout request which is intentionally camelCase to match the existing frontend
- Spring Data repositories live in app.model and extend JpaRepository, one per entity
- Unfinished API endpoints return a placeholder via Stubs.notImplemented(...) until real behaviour is implemented
- Frontend screens live one-per-file in src/screens/ with a colocated *.component.spec.ts unit test
- Frontend screens share navigate/brand via src/lib/screen-base.ts and common UI/icon primitives from src/lib/ui.ts and src/lib/icons.ts
- Backend code style is enforced via Checkstyle (checkstyle.xml) and Spotless (Google Java Format)
- Frontend code style is enforced via ESLint and Prettier
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Backend fails to build/run with a JDK version error | Install Java 21 — pom.xml pins java.version=21 and the Dockerfile builds on eclipse-temurin:21 |
| Backend starts but data doesn't persist between restarts | No DATABASE_URL was supplied, so it fell back to the in-memory H2 database; set DATABASE_URL to point at the Postgres instance from docker-compose.yml to persist data |
| Playwright e2e tests fail to launch a browser | Run npm run test:e2e:install first to fetch Chromium |
| Organiser sign-in/JWT calls fail or behave insecurely in a shared environment | The default app.jwt.secret in application.properties is an insecure dev placeholder; set JWT_SECRET_KEY (32+ chars) via environment for any non-local run |
| Frontend calls to the API return connection errors | Set VITE_API_BASE_URL to the running backend's URL (frontend/src/lib/api.ts defaults to http://localhost:8000) |
